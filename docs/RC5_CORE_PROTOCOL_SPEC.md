# INNERnet RC5 core protocol specification — implementation-aligned draft

**Implementation release:** `1.0.0`. **Status:** implementation-aligned ST81 / OB80-2 / R90 / UV10 core software contract (not independently security certified, and not yet independently reimplemented end-to-end). These rules describe the current Python implementation and are intended to support a second implementation. Where an old document contradicts this specification, the new profile identified below takes precedence. No downgrade from ST81 to ST80 is provided.

## Scope and trust

The interoperable **candidate core** is ST81 authenticated TCP, OB80-2 recipient-encrypted objects, signed R90-ROUTE-1 plans, and UV10-1 application framing. HTTP v2/v3 mesh storage and native UDP IN40/IN41 with mailbox (IN50/IE60/IO70) are **separate experimental profiles**, not transparent implementations of one unified session/transport protocol. Every node Ed25519 key, sender identity, recipient identity and R90 publisher identity used as a trust anchor MUST be pinned *independently* of the network response or recipient bundle. A cryptographically valid self-signed recipient bundle is **not** a recipient pin. Application payloads of UV10 are plaintext until enclosed in OB80 encryption. TLS, independent discovery, revocation, real-time streaming, global availability, and federated fault tolerance are not provided by the core.

## ST81 handshake (no ST80 downgrade)

All byte strings below concatenate in wire order; integers are unsigned network big-endian. Identities are Ed25519 public keys (32 bytes), ephemeral agreement keys are X25519 (32 bytes). The responder sends `S81H` (4) + its Ed25519 public key (32) + random challenge (32), **68 bytes**, before receiving the signed client hello. Client MUST check the expected pinned responder key. The initiator sends `S81C` (4) + client Ed25519 key (32) + ephemeral X25519 key (32) + client nonce (32) + Ed25519 signature (64), **164 bytes**. The client signature is over the exact bytes `INNERnet/ST80/client-auth\0` + full 68-byte server challenge + first 100 bytes of the client hello. (The domain label contains ST80 for historical compatibility but this wire profile is **ST81 only**.)

The server verifies an allowlisted client key and signature, then sends `S81S` (4) + server Ed25519 key (32) + ephemeral X25519 key (32) + echoed client nonce (32) + server nonce (32) + signature (64), **196 bytes**. Server signature covers `INNERnet/ST80/server-auth\0` + 68-byte challenge + 164-byte client hello + first 132 bytes of its reply. Initiator verifies signature, pinned identity and echoed nonce. Both parties compute fresh X25519 shared secret and HKDF-SHA256, output length 64, salt `SHA256(challenge || hello || reply)`, info `INNERnet/ST80/key-schedule-v1\0`. First 32 bytes are C→S key; second 32 S→C key. The server consumes a ChaCha20-Poly1305 client key-confirmation frame with JSON header `{"handshake":"key-confirm-v1"}`, empty body, and returns an authenticated `{"handshake":"key-confirmed-v1"}` frame with empty body. No authenticated application slot is assigned before this check.

A handshake has a **total** monotonic deadline: server 2 seconds, client its configured timeout, including confirmation. Confirmation ciphertext frame is bounded to 512 bytes. Each later session frame is `uint32(ciphertext_length) || AEAD(cleartext)` where cleartext is `uint32(json_length) || JSON || raw_body`, maximum ciphertext 400,000 bytes and JSON 240,000 bytes. JSON must be object-shaped, contain no duplicate keys, reject NaN/Infinity including floating-point literals that overflow to non-finite values (such as `1e400`), use signed 64-bit integers, and have no nested object/array depth exceeding 64. Nonconforming JSON frames are rejected before request dispatch. Each direction begins at counter zero and uses nonce `u32(0)||u64(counter)` with AAD `b"C"/b"S" || u64(counter)`, independently for send and receive. Failure of identity, signature, key confirmation, AEAD, framing, or counters MUST close the connection without an ST80 fallback. The server limits both pre-auth and active sockets. These limits mitigate but cannot eliminate network-layer flooding.

## OB80-2 signed recipient-only encrypted objects

Manifest has wrapper `{"payload":{...},"signature":"<128 hex>"}`, with Ed25519 signature over `INNERnet/OB80/signed-object\0` + canonical JSON payload (sorted keys, compact separators, ASCII escaping, NaN excluded). Payload has exactly: `version`, `object_id`, `sender`, `recipient`, `ephemeral_x25519`, `size`, `chunk_size`, `chunks`, `ciphertext_hashes`, `sealed_sha256`, `created_at`, `expires_at`. New objects MUST have `version="OB80-2"`; signed `sender` and `recipient` are 32-byte lowercase hex keys. Each 16-byte object ID MUST equal the first 16 bytes of SHA256(`INNERnet/OB80/v2/sender-scoped-id\0` + sender_pub32 + sender_ephemeral_pub32). The receiver MUST verify this binding before storage. `OB80-1` is a read/forward compatibility profile for already-existing objects; new OB80-1 publishing is restricted to trusted relay paths and MUST NOT be treated as sender-scoped.

Input size 1..134,217,728 bytes, chunk size exactly 65,536 bytes, count ceil(size/chunk_size), with max 2048 chunks. Each ciphertext chunk has length clear_length+16 and its SHA-256 must match the manifest's `ciphertext_hashes` entry before decryption. Sender uses an independently pinned recipient IE60 bundle: verifying that bundle with its own `identity_ed25519` field is **not sufficient**. Ephemeral X25519 shared secret is expanded by HKDF-SHA256: length 32, salt SHA256(object_id16||sender_pub32||recipient_pub32), info `INNERnet/OB80/object-x25519-v1\0`. Chunk AEAD is ChaCha20-Poly1305, nonce u32(0)||u64(chunk_index), AAD `INNERnet/OB80/chunk\0` + object_id + sender + recipient. Sealed SHA256 digest is encrypted under all-0xff 12-byte nonce with AAD `INNERnet/OB80/sealed-digest\0` + chunk AAD. The recipient verifies sender pin, recipient identity, per-chunk fingerprints, AEAD, whole-object plaintext digest and exclusive output publication.

One original sender, or explicitly trusted configured legacy-forwarding relay, may forward ciphertext to another allowlisted node. Storage commitment is not a delivery or durability guarantee. `get-range-v1` may reduce RPC count, but all ciphertext and all manifest checks remain mandatory. If the peer does not advertise it, clients may use individual `get` calls; malformed authenticated peer replies MUST fail over to the next **pinned** peer without weakening sender verification. Local resume checkpoint databases contain ciphertext only and are owner-private.

## R90-ROUTE-1 / R90-ROUTE-2

A previously signed plan is still accepted until expiry even if the publisher issued a newer plan; R90-ROUTE-1 has no rollback-prevention state. Treat routes as availability/metadata hints, not revocable grants.

**R90-ROUTE-2** is an additive profile that adds a mandatory monotonic `sequence` (unsigned 64-bit) field to the signed payload (`version="R90-ROUTE-2"`, field set `{version, sequence, issued_at, expires_at, nodes, routes}`). A verifier holding client-side per-publisher sequence state (`routing_v090.SequenceStore`) MUST reject any ROUTE-2 plan whose `sequence` is `<=` the highest previously accepted from that pinned publisher, preventing replay/rollback of an older unexpired plan over a compromised delivery channel. ROUTE-2 does not add revocation. ROUTE-1 remains valid for read/forward compatibility with no anti-rollback. See `MIGRATION_ROUTE2.md`.

Route wrapper: `{"payload":..., "publisher":"<64 hex>", "signature":"<128 hex>"}`. Publisher signs `INNERnet/R90/signed-route-plan\0` + canonical payload JSON, and caller MUST verify an independently pinned publisher key. Payload has `version="R90-ROUTE-1"`, `issued_at`, `expires_at`, `nodes`, `routes`. Nodes: 1..32 unique `id`, `host`, `port` 1..65535, `public_ed25519`, and self-declared `failure_domain`. Routes: 1..128 entries of `recipient` (32-byte Ed25519 lowercase hex) and `ordered_nodes` (unique node IDs in preference order). Expiry required; 60..86400 second validity, future issuance tolerance <=300 seconds. Failure domains are **assertions**, not verified provider independence. Per-peer malformed responses are availability failures, not proof to accept unsigned content.

## UV10-1

`ASCII UV10` (4) + uint32 header length (2..4096) + canonical sorted-key compact ASCII-escaped JSON + payload (`size` bytes). No trailing bytes; total file size <=128 MiB. Fields exactly `version`, `kind`, `content_type`, `name`, `size`, `sha256`, `created_at`, `stream_id`, `sequence`, `final`, `attributes`. Kinds file/message/event/stream-segment. `message` must be UTF-8 <=65536 bytes; `event` must be UTF-8 JSON <=65536 bytes, both checked at **unpack** as well as at creation. Display names/attributes disallow control and surrogate codepoints. Receivers validate complete framing, digest and application type. Stream segments are finite ordered files; not low-latency streams. A Go implementation of UV10 (`interop/go/uv10verify`) and of ST81 (`provider/st81.go`, used by the provider and relay) exists; ST81 is conformance-tested against this Python reference in both directions (`tests/test_st81_go_interop.py`). Both were written by the same project, so they are a second implementation, not an independent review. OB80 and R90 have no second implementation yet. See `SPEC_UV10_APPLICATION_V1_CANDIDATE.md` for field bounds and `UV10_TEST_VECTOR.json` for an exact framing vector.

## Error and version evolution

Malformed/untrusted handshakes and AEAD failures fail closed. ST81 JSON RPC uses an authenticated header with `rid`, response status and optional raw bytes, with a global 400000-byte ciphertext bound. Existing RPC error payloads contain bounded free-form strings and therefore are **not frozen machine-readable error codes**. A compatible external implementation MUST NOT rely on particular error string text; it MUST implement structural rejection and identity pinning. New incompatible formats MUST receive distinct version/magic identifiers and migration instructions. Operators MUST NOT enable transparent downgrade from ST81 to ST80 or from sender-scoped OB80-2 creation to OB80-1 creation.

## Security and evidence boundaries

No independent ST81/OB80/R90 implementation, professional cryptographic review, independent-provider outage qualification, or full public-WAN operational validation is established by this specification or included tests. These remain external release gates. This is an **implementation-aligned wire specification** for the scoped core release, not proof of independent cross-language interoperability. All values and local demonstrations are synthetic.
